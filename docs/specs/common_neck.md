# 共通部品：首の調停（v1）

ID には紐づかない共通部品（#0）。ID9・ID15・ID16・ID25 が共通で使う。

## 目的

首（servo1 左右／servo2 上下）は、目と超音波センサーの両方を載せているため、
「安全のために正面へ固定したい」「測るために向けたい」「表情として動かしたい」が
同時に起きる。これを優先度で1つに決める。

設計原則2（CLAUDE.md）：
首の使用権は「安全＞測距＞表情」の順。走行中は首を正面・水平に固定し、
見回しは停止中（または減速中の短時間）のみ。首が動いている間と、
止まってから安定するまでの測距値は無効扱い。

## 使用権の優先度

| 持ち主 | 優先度 | 使う場面 |
|---|---|---|
| 安全（SAFETY） | 30 | 走行中に正面・水平へ固定する |
| 測距（RANGE） | 20 | 停止中の見回し（ID15・ID16） |
| 表情（EXPRESSION） | 10 | 首かしげ・見上げるなど（ID3・ID10） |

- 申し出（`Neck_Request`）は、自分より優先度の高い持ち主がいれば断られる（角度は変わらない）。
- 同じ持ち主からの申し出は常に通る。使い終わったら `Neck_Release` で返す。
- v1 で実際に使うのは安全だけ。測距・表情の枠はスプリント2以降のために用意する。

## 「首が安定した」の判定

測距値を信用してよいのは、首を動かす命令を出してから一定時間が経った後とする。

待ち時間 ＝ `NECK_SETTLE_BASE_MS` ＋ 動かした角度 × `NECK_SETTLE_PER_DEG_MS`

（動かした角度 ＝ 左右・上下の変化量の大きいほう）

### 実測との対応（docs/measurements.md：首の停止後の安定時間）

測定の 0ms は「正面へ戻す命令を出した時刻」なので、実測値は首が動く時間も含んでいる。

| 振り幅 | 実測 平均 | 実測 最長 | この式の値 |
|---|---|---|---|
| ±20° | 12ms | 60ms | 100ms |
| ±40° | 44ms | 60ms | 140ms |
| ±55° | 104ms | 160ms | 170ms |

- `NECK_SETTLE_BASE_MS = 60`：±20°・±40° の実測の最長がどちらも 60ms。
- `NECK_SETTLE_PER_DEG_MS = 2`：±55° で 60＋55×2＝170ms となり、実測の最長 160ms を上回る。
- ±20° は 5回中4回が「0ms」だったが、これは首が一瞬で止まった証拠ではない。
  超音波の指向角が広く、首を振っても同じ壁の最近点を見ていたため、値が変わらなかった
  可能性が高い。そのため小さい動きでも `BASE` の 60ms は必ず待つ。
- servo2（上下）の安定時間は未測定。当面は servo1 と同じ式を使う（スプリント2以降で確認）。

### 測距値の扱い

- 首が安定していない間に完了した測距は、障害物の判定に使わない。
- 首が動き始めたら、それまでの測距の履歴を捨てる（`Obstacle_Reset`）。

```
void Neck_Release(NeckOwner owner);

bool Neck_IsSteady(unsigned long nowMs);   // 首が止まっていて、測距値を信用してよいか
bool Neck_IsFront(void);                   // 正面・水平か（走り出す条件）
void Neck_Update(unsigned long nowMs);
```

- 角度の丸め（可動範囲）は今までどおり `hal/hal_servo.*` が行う。
- 現在と同じ角度を申し出たときは、首を動かさず、安定待ちもやり直さない
  （走行中は安全が毎ループ正面を申し出るため）。

## 完了条件

- 動作：走行中は首が正面・水平から動かない。首を動かした直後の測距値が判定に使われない。
- シリアルに、首の角度・使用権の持ち主・安定／動作中の別が出る。

## 首が動かない回がある（2026-10-10 の調査。コードの読み取り。原因は未確定）

見回しの試験（キー `o`）で、首への指示60回のうち4回、左右へ向ける指示が実際の動きにつながらなかった（measurements.md）。
`Neck_Request` → `Servo_SetAngle` → PCA9685 への書き込みまでを追った。

### 書き込みの経路

1. `Neck_Request(持ち主, 左右, 上下)`：優先度で断られなければ、**毎回** `Servo_SetAngle` を左右・上下の順に呼ぶ。
   「同じ角度なら省く」のは安定待ちのやり直しだけで、書き込みは省かない。
2. `Servo_SetAngle`：可動範囲に丸める（左右 20〜140°、上下 90〜140°）→ パルス幅に換算（`map(角度, 0,180, 102,512)`。
   84°＝293、134°＝407、34°＝179、上下 98°＝325）→ `Pca9685_SetPulseWidth`。**ここにも「変わらなければ書かない」はない。**
3. ライブラリ `setChannelPulseWidth` → `setChannelOnAndOffTime`：ON＝0、OFF＝パルス幅を、
   レジスタ `0x06 + 4×チャンネル` から4バイト（ON_L・ON_H・OFF_L・OFF_H）で1回の通信で書く。左右は ch0（0x06〜0x09）、上下は ch1（0x0A〜0x0D）。

### 調べた経路と結果

| 調べたこと | 結果 |
|---|---|
| 角度が変わらないと判断して書き込みを省く | **ない**（サーボ側）。モーター側（`Motor_DrivePwm`）だけ、前回と同じ PWM なら書かない |
| 値の丸め・範囲の制限 | 134°・34° は範囲内で、そのまま 407・179 になる。丸めで正面の値になる経路はない |
| モーターの書き込みがサーボのチャンネルに影響する | **見つからない。** モーターは ch8〜15 に、チャンネルごとに4バイトずつ書く。全チャンネルへの書き込み（0xFA〜）は使っていない。オートインクリメントで進むのは4バイトの中だけで、隣のチャンネルにはみ出さない。見回しの試験中はモーターの値が変わらないので、そもそも書いていない |
| 再初期化・スリープ・周波数の設定が動作中に走る | **ない。** `Pca9685_Setup()` は起動時の1回だけ（`Hal_Setup`）。スリープと周波数の設定はその中だけ |
| ab92acb（タイムアウト 5ms・失敗を数える改変） | 送る内容・順番は変えていない。タイムアウトや NACK なら失敗として数えるが、`t` の PCA9685 の失敗は 0 |
| 2026-10-03 の初期化の書き直し（ca01732） | 前は MODE1 に 0x00 を書いていた（AI も落ちる）が、そのあとの周波数設定で AI＝1 に戻っていた。今は ALLCALL だけ落とす。最終の状態は同じ。動作中の書き込みは変えていない |
| まばたき・ジャイロと同じバスで重なる | I2C を使うのは loop の中だけで、割り込みからは使っていない。通信は1つずつ順に行われ、途中で混ざらない |

### コードでは分からないこと

- **書いた値が IC に正しく入ったか。** I2C はバイトごとの ACK しかなく、内容の誤りは検出できない。失敗 0 は「応答はあった」までしか示さない。
  書いたあとの読み戻しも、書き直しもしていない。
- **左右へ向ける指示は、1回しか書かない。** 見回し（`NeckScan`）は使用権を取れたら `Neck_Request` を呼ぶのをやめるので、その1回が効かなければ、
  その方向の測距が終わるまで首は前の向きのまま。一方、正面へ戻す指示（ID25 の「正面へ戻す」、安全層の走行中の固定）は、毎 loop 書き直している。
  **「左右は時々動かず、正面は必ず動く」という結果と合う**（合うというだけで、原因と決まったわけではない）。
- IC より先：サーボの電源・サーボ自体・配線。
- PCA9685 が出力を切り替えるタイミング（MODE2 の OCH。既定は STOP で反映）は、**記憶による**。データシートでは確かめていない。

### 切り分け（見回しの試験に足した読み戻し）

各方向の測距を終えた時点で、左右・上下のサーボのチャンネルを PCA9685 から読み戻し、書いたはずの値（ON＝0・OFF＝パルス幅）と比べる。

- 不一致がある → 指示が IC に正しく届いていない（ソフトか通信）。
- 全部一致なのに首が動かない回がある → IC より先（サーボの電源、サーボ自体、配線）。

読み戻しのレジスタ（`0x06 + 4×チャンネル` から4バイト、ON_L・ON_H・OFF_L・OFF_H）は、**ライブラリのソース**
（lib/PCA9685/src/PCA9685.h の `LED0_ON_L_REGISTER_ADDRESS`・`LED_REGISTERS_SIZE`、PCA9685.cpp の `getChannelOnAndOffTime`）で確認した。
データシートは今回は開いていない（書き込みと同じ番号・同じ並びを、ライブラリの関数で読むだけ）。

対策の候補（切り分けのあとで決める。まだ入れていない）：見回しの間、左右の角度を毎 loop 書き直す／書いたあと読み戻して違えば書き直す／
測った値が正面と同じなら測り直す。

- 【2026-10-11 追記】「毎 loop 書き直す」「読み戻して違えば書き直す」は、**効かない見込み**。
  読み戻しが全部一致だったので、IC には正しい値がすでに入っている。同じ値を書き直しても、IC の出力は変わらない。
- 「測った値が正面と同じなら測り直す」は、原因を直さないが、誤った値を使わないための手当てとしては残る
  （左右が本当に正面と同じ距離のときと区別できない点に注意）。

### 切り分けの結果（2026-10-11、キー `o`、4d6cc49。数字は measurements.md）

- 左が測れなかった回が4回（9・10・11・13回目）、右は0回。読み戻しは20回 × 3方向すべて一致（正面 293／左 407／右 179）、打ち切り 0。
  目視でも、左を向かない回が4回程度。
- **指示は IC に正しく入っているが、サーボが動いていない。原因は IC より先**（サーボの電源・サーボ自体・配線）。
  上の「左右へ向ける指示は1回しか書かない」は、原因ではなかった。
- 13回目は、左への指示の 87ms 後にジャイロ 0.0dps・電池 8.03V（動いた4回目は 98ms 後に +8.6dps）。電池の電圧は落ちていない。
  同じ回の右は毎回動いている。
- まだ分からないこと：動かないのが「左」という向きによるのか、「正面のあとの最初の動き」という順番によるのか。
  → 順番を逆にした試験（キー `i`：正面 → 右 → 左）を足した。右が動かなくなれば順番、左のままなら向き（左へ 50° 動く指示そのもの）。
- 首が実際に動いたかの目安として、左右それぞれの指示の直後 150ms（`DEBUG_SCAN_GYRO_WINDOW_MS`）のジャイロの最大の絶対値を、
  各回の行に出すようにした（`o`・`i` の両方。動いた回は数 dps、動かなかった回はほぼ 0 の見込み。1回ずつの例からの見込みで、しきい値は決めていない）。

### 切り分けの結果その2（2026-10-11、b8cb7c4、キー `o`・`i`。数字は measurements.md）

- 首への指示60回のうち7回で、首が動かなかった。読み戻しは180回すべて一致。**動かないのは「正面で止まったあとの最初の指示」。**
  向き（左）の問題ではなく、順番の問題に見える（前回は左に偏っていたが、今回は最初の指示に付いている）。
- 2つ目の指示にも、指示から 150ms 以内には反応しないが、遅れて動く。
- `Neck_Request` は、左右（ch0）→ 上下（ch1）の順に、続けて2回の通信で書く。上下は毎回同じ値（325）。
  **仮説：左右を書いた直後の上下への書き込みが、IC の出力への反映に影響している。**
- 確かめる実験：キー `k` で「上下のサーボへの書き込みを省く」を入にする（起動時は切＝今までどおり）。
  入のときは、上下の角度が今の値と同じなら PCA9685 へ書かない（値が変わるときと、左右の書き込みは今までどおり）。
  読み戻し（左右・上下）は入のときも行う。入／切の状態は、見回しの試験の開始の行・各回の行・まとめの行に出る。
  うろうろの動きは変えていない（切り替えは起動時に切）。
- 首の動き出しを見るために、`o`・`i` の各回の行に「動き出すまでの時間」を足した。首へ指示を出すたび（1つ目・2つ目・正面へ戻す）に、
  指示からジャイロの絶対値が初めて `DEBUG_SCAN_ONSET_DPS`（【仮】2.0dps）以上になるまでの時間（ms）。見る範囲は次の指示を出すまで
  （正面へ戻す指示は最大 `DEBUG_SCAN_ONSET_FRONT_MS` ＝1000ms）。超えなければ「-」。まとめに、指示ごとの最小・最大・「-」の回数が出る。
  **試験での記録だけで、動きの判断には使わない。**
- **方針：ジャイロで首の動きを確かめる方法は、対策には使わない。** 走行中に首を動かす場面では、車体の動きと首の反動を分けられず使えないため。
  ジャイロは、止まった車体での切り分けの目安にだけ使う。
- 対策候補のうち、「見回しの間、左右の角度を毎 loop 書き直す」「書いたあと読み戻して違えば書き直す」は、読み戻しが全部一致だったので**効かない見込み**
  （2026-10-11 の1つ目の追記のとおり）。

### PCA9685 の出力への反映のタイミング（データシート NXP PCA9685 Rev.4 で確認。2026-10-11）

データシートの PDF（https://www.nxp.com/docs/en/data-sheet/PCA9685.pdf。表紙は「Rev. 4 — 16 April 2015」）の文章を、テキストに起こして読んだ。

**確認できたこと**

- **MODE2 の bit3（OCH）**（7.3.2節、Table 6、15ページ）：0（既定）＝「Outputs change on STOP command」、1＝「Outputs change on ACK」。
  - 脚注 [2]：STOP で反映するのは、06h（LED0_ON_L）〜45h（LED15_OFF_H）のレジスタだけ。「1つ以上のレジスタを、どの順でもよいので、STOP の前に書ける」。
    複数の PCA9685 の出力をそろえて変えるための仕組み。
  - 脚注 [3] と 7.3.3節（16ページ）：ACK で反映する場合は、**その LED チャンネルの4つのレジスタすべてが書かれてはじめて、最後の ACK で出力が変わる**。
  - 特徴の欄（2ページ）：「Output state change programmable on the Acknowledge or the STOP Command to update outputs byte-by-byte or all at the same time
    （既定は Change on STOP）」。
- **Nova のコードは MODE2 を書き換えていない**（`Pca9685_Setup` は `setupSingleDevice`（ソフトウェアリセット）と `setToFrequency` だけ）。
  リセット後の MODE2 は既定なので、OCH＝0（STOP で反映）のはず。**ただし実機で MODE2 を読んで確かめてはいない**。
- したがって Nova の書き込み（チャンネルごとに4バイトを1回の通信で書き、通信の終わりが STOP）では、**左右（ch0）の書き込みの STOP で ch0 が、
  続く上下（ch1）の書き込みの STOP で ch1 が、それぞれ別々に反映される**（と読める。実機での確認はまだ）。
- 7.3.1.1節（RESTART）：OCH＝0 のときは、PWM レジスタへ書いて STOP を出すと RESTART ビットが消える（「write to any PWM register then issue an I2C-bus STOP」）。
  OCH＝1 のときは、1チャンネルの4レジスタすべてを書くと消える。これも「反映は STOP（または4つ目の ACK）のとき」という読みと合う。

**確認できなかったこと**

- **PWM の周期（約 20ms）の途中で書いたときの扱い**（次の周期の頭まで待つのか、すぐ反映するのか）：**文章には書かれていない。**
  図10・図11（19〜20ページ、「Update examples when LEDn_ON < LEDn_OFF」「LEDn_ON > LEDn_OFF」）に
  「register(s) updated in this cycle」「output(s) updated in this cycle」という注記があり、「書いた周期」と「出力が変わる周期」を区別した図に見える。
  ただし**図は画像として開けず（画像にする道具がなく、テキストにした分だけを読んだ）、断定できない。**
  図を人の目で見て確かめる必要がある（20ページ前後）。
