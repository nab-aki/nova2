## 2. 次にやること（順番）

1. **その前に：`Motion_IsTurning()` が片側旋回で本当に true を拾えているかの確認**
   （2026-09-23の5分間試験で、ID9停止11回のうち「回転中」がずっと0回だったため）。
   - **原因の見込み（コードで確認済み）**：`core/arbiter.cpp` の `Arbiter_Update()` は、同じレイヤーの
     振る舞いが交代するとき「古い振る舞いの `onStop()` → 新しい振る舞いの `onStart()`」の順で呼ぶ。
     `WanderBehavior::onStop()`（[wander.cpp:80](src/behaviors/wander.cpp#L80)）は状態に関わらず
     無条件で `Motion_Stop(nowMs)` を呼んでおり、コメントにも「回転中ならここで取り消される」とある。
     つまり ID9 が片側旋回に割り込むときは、`NoticeBehavior::onStart()`（`EnterNoticed()`）が
     `Motion_IsTurning()` を読む**前**に、その場で `turning=false` にリセットされてしまう。
     これが「回転中0回」のまま変わらない実際の原因である可能性が高い。
   - `Motion_IsTurning()` 自体が片側旋回で true になること（`TurnKind` によらず一律 `turning=true`）は
     コードレベルで確認済み（2026-09-22、Motion_StartTurn実装確認）。問題は**タイミング**の方。
   - 直すなら、Wanderの`onStop()`が回転を取り消す**前**の状態（回転していたかどうか）を、
     NoticeBehavior側に渡す・別の場所で判定するなどの案が考えられる（要検討）。
2. **回転の値をまとめて見直す**（「片側旋回の値の見直し」に、キック時間短縮による回転角の実測も統合）：
   - その場回転：キック300msでの1ステップの角度を測り直す（`TROUBLE_MAX_STEPS` 12回も見直す）。
   - 片側旋回：保持（1450）がキック（1400）より大きく、キックの意味が薄い（実質 1450 一定）。
   - `WANDER_RECOVER_PAUSE_MS`（500ms、仮の値）も、動きの印象を見ながら詰める。
   - デバッグの調整キー（`3`〜`6`、一時停止中の `q a w s e d r f`）で床の上で探す。
3. ロードマップの次：**ID26 詰まり脱出**。着手時に、`docs/catalog.md` の概要を実測に合わせて見直す

## 3. 5分間試験の結果とブラウンアウトの経緯（スプリント2、計4回＋原因調査）

- **正面衝突は4回とも0回。** 最優先方針（障害物を避けながらうろうろする）の核心は崩れなかった。
- 1回目：片側旋回が浅い角度の壁に止められ続けて張りつく問題（173秒中14回中断）。
  → 対策：横がとても近いときは後退+その場回転で避けるようにした（2026-09-22）。
- 2回目：張りつきは解消したが、後退+その場回転の直後にブラウンアウトで再起動。
  → 対策（案B）：その場回転のキック時間短縮（1000ms→300ms）、後退と回転の間に「ため」
  `WANDER_RECOVER_PAUSE_MS`（500ms）を追加（2026-09-22）。
- 3回目：案Bを入れても再発。しかも落ちた回の集計はNVS保存前に消えるため、何の動作中に落ちたか
  分からなかった。→「足あと」（RTCメモリ＋NVS退避。common_trace.md）を追加（2026-09-22〜23）。
- 4回目（足あと導入後）：ブラウンアウトは起きなかった（`起動:電源投入`、経過462694ms）。
  `t` に出た保存データは前回の書き込み時の無関係な古い記録と判明（表示のみ修正。案A、2026-09-23）。
- **原因の特定**：ソフト側の対策（案B）だけでは解決しておらず、**電源配線の一部がAWG26相当と
  細かったことが根本原因**と判明。**AWG16へ交換したところ、満充電・ケーブルなしの5分間試験
  （経過307788ms）でブラウンアウトが再発せず完走した**（decisions.md・measurements.md 2026-09-23）。
- **案B（後退と回転の間の「ため」500ms）はそのまま残す**：ブラウンアウトの直接の解決策ではなかったが、
  実機で見た動きが不自然でなく、「動く前に小さなためを入れる」という設計原則3に合うため
  （decisions.md 2026-09-23）。
- 教訓：**電流が大きい動き（回転・旋回のキックなど）で電圧関連の不具合が疑われたら、ソフトの
  「ため」だけでなく配線の径（電流容量）も早めに疑うこと。**

## 5. 未解決の点・注意

- **`DEBUG_START_PAUSED` は 1**（config.h）。起動直後は一時停止で、▶ か `p` で開始する。
  ケーブルなしの試験ではこのまま便利。すぐ動かしたいときは 0 にする。
  試験の集計は、起動時に一時停止のままだと「再開」まで始まらない（1で始まる設定と整合させてある）。
- **書き込みは、ユーザーが指示したときだけ。書き込み前にユーザーがシリアルモニタを閉じる**（COM3 が使用中だと失敗する）。
  書き込みは `~/.platformio/penv/Scripts/pio.exe run -t upload --upload-port COM3`（fnk0053）。
  `pio.exe device list` でポートが見えないときは、USBケーブル・本体の電源を確認する。
  ビルドだけは `pio run`。ホストに g++ はない。
- **持ち上げ中（ライン111）は、`3`〜`6` も受け付けない**（安全層が止める）。床に置いて 111 が消えてから使う。
- 回転キー `3`〜`6` の1ステップの間だけ、障害物「あり」による停止を外している（デバッグ用。非常停止12cm未満と持ち上げは残す）。
  本番の ID25・ID15 は外さない。
- **書き込みで、調整キーで変えた値は元に戻る**。値を決めたら config.h に反映する（ユーザーの指示で）。
- ID15 の既知の限界：後方にセンサーがない／狭い場所では一周しても空かないことがある／浅い角度の壁は見つからないことがある。
- ID25 の片側旋回が途中で止められたときは、`[うろうろ] 片側旋回…中断` の行が出る（①ID9に交代、②安全層に止められた）。
  試験の集計では、どちらも「旋回中断」として1つにまとめて数える。後退+その場回転（張りつき対策）が
  途中で交代されたときは別の行・別カウント（`後退回転 実施/中断`）で、優先度35のため通常は一時停止のときだけ出る。
- **`WANDER_SIDE_VERY_NEAR_CM`（25cm）は仮の値**。実機で見回しのログ（横の距離）を見ながら詰める
  （`WANDER_SIDE_NEAR_CM` 40cm との間の使い分けが妥当か）。
- 30°より浅い壁は検知できない（ID25 の見回しと ID26 で対処）。45°の壁は近距離で遠く出る（実測）。
- 電池 7.0V は仮の動作下限（余裕の計算に使った。ID22 で見直す）。走行中の電池電圧の読み取りは乱れる（回転中の 6.40V も同じ可能性。判定には使わない）。
- IR：GPIO0 は起動時のモード選択（strapping）のピン。起動の瞬間にリモコンを押さない。ライブラリは `lib_deps`（初回ビルドはネットワークが必要）。
- 試験の集計・足あとはNVS（フラッシュ）に書く（キーは `STORAGE_KEY_TEST_STATS`・`STORAGE_KEY_TRACE`、
  名前空間は共通の "nova"）。`Preferences` は Arduino-ESP32 のコアに含まれるので `lib_deps` は不要。
  `TestRecord`・`TraceSaved` の構造を変えると、保存済みのデータは読み捨てられる（`magic` で判定）。
- **リセット理由**（`hal/hal_reset.*`）は `esp_reset_reason()`（ESP-IDF、`esp_system.h`）のラッパー。
  `Preferences` と同じくコアに含まれるので追加の `lib_deps` は不要。試験は再起動をまたがないので、
  試験を始めるたびに1回だけ刻む（ブート中に値が変わることはない）。
- **足あと**（`hal/hal_trace.*`）は `RTC_NOINIT_ATTR`（RTCスローメモリ）を使う。電源が入ったままの
  再起動（ソフトリセット・ウォッチドッグ・ブラウンアウト）では消えないが、電池を外すなど電源を
  完全に切ると内容は不定になる（`magic` で判定）。`t` で見られるのは車体レイヤーの振る舞い・状態の
  交代だけ（目のレイヤーはまばたきが頻繁でリングを埋めるため記録していない）。
- 作業のコツ：ファイルの作成・編集は Write／Edit ツールで行う。bash のヒアドキュメントは引用符やバックスラッシュで壊れることがあった。
  作業ツリーの改行は CRLF と LF が混在する（Git の自動変換）。Python で直すときは改行を正規化してから置換する。
